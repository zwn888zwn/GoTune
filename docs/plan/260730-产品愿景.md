对，真正的愿景不是：

> **在 VS Code 里做一个更漂亮的 pprof Viewer。**

而应该是：

> **像调试功能 Bug 一样，调试 Go 的性能问题。**

最终体验应该是：

```text
启动或连接 Go 服务
→ 选择“我遇到了什么问题”
→ 跑一次真实操作或压测
→ GoTune 自动采集合适的证据
→ 瓶颈直接显示在源码旁边
→ 告诉你为什么可疑、下一步看哪里
→ 修改代码
→ 用完全相同的场景重新跑
→ 告诉你到底有没有改善
```

这其实就是最初设计文档的核心：`哪里慢 → 为什么慢 → 怎么改 → 是否真的变快`，而不是把 CPU、Heap、Mutex、Trace 做成一排按钮。

# 一句话定位

**GoTune 是 VS Code 里的 Go 性能 Debugger。**

pprof 仍然是底层证据来源，但用户不需要先理解：

- 现在该抓 `inuse_space` 还是 `alloc_space`；
- 该看 CPU 还是 Block；
- Mutex 图里为什么标的是 `Unlock`；
- 一个函数 cumulative 很高到底是不是它本身慢；
- 两份 Profile 到底能不能直接对比。

官方 pprof 提供 CPU、Heap、Goroutine、Block、Mutex 等运行时证据；其中 CPU 只表示真正占用 CPU 的时间，不包含睡眠和 I/O 等待，Block 表示同步原语上的等待，Mutex 表示锁竞争。GoTune 的价值是自动选择、组合、解释这些证据，并把它们落回源码。

可以简单理解成：

```text
pprof：给你检查报告和影像
GoTune：带你定位病灶、打开对应代码、修改后复查
```

# GoTune 的核心对象不应该是 Profile，而应该是“性能场景”

现在插件主要围绕一个个 Profile Session 展开。最终应该围绕一个可重复的 **Performance Scenario** 展开：

```text
性能场景
├── Target：哪个程序、怎么启动
├── Workload：怎样复现问题
├── Warmup：预热多久
├── Capture：采集哪些证据、采集多久
├── Success Metrics：怎样才算变好
└── Baseline：修改前是什么表现
```

例如你的 VPN 服务端可以保存一个场景：

```text
场景：VPN 500 路流压测

目标：
  VS Code Launch Configuration: VPN Server Dev

预热：
  10 秒

压测：
  VS Code Task: vpn-load-500
  或 go run ./cmd/loadgen -streams 500 -duration 30s

自动采集：
  CPU 30 秒
  Allocation delta 30 秒
  Heap 压测前后快照
  Mutex / Block delta
  Goroutine 前后快照
  GC 和运行时趋势

成功指标：
  吞吐 Mbps
  p95 延迟
  CPU
  alloc/GB
  Heap 增长
  Mutex wait
  Goroutine 数量
```

以后不是每次重新想“该点哪个按钮”，而是：

```text
打开项目
→ Run “VPN 500 路流压测”
→ 等压测完成
→ 查看源码瓶颈
```

这才是一个开发者会长期使用的工具。

# 场景一：排查内存泄漏

## 用户怎么操作

你只需要选择：

```text
Investigate → Memory keeps growing
```

然后：

```text
启动服务
→ 执行一段真实业务操作
→ 或者运行压测任务
→ 点击结束分析
```

不应该要求用户先决定抓 Heap 还是 Alloc。

## GoTune 在背后做什么

它自动组合：

1. 压测前 Heap 基线；
2. 压测过程中的 Allocation delta；
3. 多轮 Heap 快照；
4. 本地测试环境可在快照前执行 GC；
5. Goroutine 数量和重复栈趋势；
6. GC 次数、Heap、Allocation rate 趋势。

`net/http/pprof` 本身支持在 Heap 快照前触发 GC，也支持按指定时间生成 alloc、heap、block、mutex 等 delta profile。当前 GoTune README 已经有三轮 GC 后的内存增长检查和 Goroutine 多轮检查，这些能力可以直接被组织进该工作流。

然后插件先帮助你判断是哪一类问题：

### A. 真正的存活内存持续上涨

```text
Heap after GC：

第 1 轮：126 MiB
第 2 轮：168 MiB
第 3 轮：211 MiB

结论：
压测停止并执行 GC 后，存活内存仍连续增长。
疑似存在对象长期被引用。
```

### B. 不是泄漏，只是分配太猛

```text
alloc_space：2.8 GiB / 30s
inuse_space：稳定在 130 MiB

结论：
存活内存稳定，没有明显泄漏。
主要问题是临时对象过多，导致 GC 压力。
```

### C. Goroutine 泄漏带着对象一起泄漏

```text
Goroutine：
320 → 670 → 1,020

其中 700 个 Goroutine 停在：
session.go:132
<-ctx.Done()

对应调用路径：
acceptLoop
→ newSession
→ startReadLoop
```

这时问题可能不是某个 `[]byte` 单独泄漏，而是 Session Goroutine 没退出，闭包、连接、Buffer 都被一起保留。

## 源码旁边应该看到什么

例如打开 `session.go`：

```go
func (m *Manager) AddSession(id string, conn net.Conn) {
    s := newSession(conn)
    m.sessions[id] = s
    go s.readLoop()
}
```

理想中的编辑器效果：

```text
m.sessions[id] = s
────────────────────────────────────────────
GoTune · Live Heap
+38.4 MiB across 3 post-GC captures
+18,624 live objects
Allocation path:
acceptLoop → AddSession → newSession
[查看调用链] [查看相关 Goroutine] [标记为修复目标]
```

在 `go s.readLoop()` 上方：

```text
GoTune · Goroutine Growth
+512 goroutines · same stack in 3 captures
Related live heap growth: +31.6 MiB
[查看完整栈] [查找退出路径]
```

你不需要在火焰图里找函数名，再手动切回 VS Code 搜代码。

## 修改后怎么验证

例如你补上：

```go
defer delete(m.sessions, id)
defer conn.Close()
```

重新运行同一个场景后：

```text
                         Before       After       Delta
Live heap growth         +84 MiB      +3.1 MiB    -96.3%
Goroutine growth         +512         +2          -99.6%
Allocation rate          92 MiB/s     74 MiB/s    -19.6%
```

然后源码旁边的提示从“持续增长”变成：

```text
Verified · no persistent growth in the last 3 captures
```

## 这里不能过度承诺

标准 Go Heap Profile 能告诉你：

- 哪些调用栈分配了存活对象；
- 哪些函数贡献了大量存活内存；
- 多轮采集后哪些对象持续增长。

但它不像某些 JVM Heap Dump 工具那样天然提供完整的“对象 A 被 Map B 的字段 C 引用”对象图。因此 GoTune 应该显示：

> 疑似泄漏分配位置和相关运行时证据

而不是假装仅凭 pprof 就百分之百知道精确持有者。

# 场景二：排查死锁、卡住和锁竞争

用户看到的入口应该是：

```text
Investigate → Request stuck or possible deadlock
```

而不是先让用户选 Goroutine、Block、Mutex 或 Trace。

## GoTune 自动组合的证据

它可以依次做：

```text
第 1 次 Goroutine 快照
等待数秒
第 2 次 Goroutine 快照
第 3 次 Goroutine 快照
Block delta
Mutex delta
必要时再 Capture Trace
```

Block Profile 记录 Goroutine 在 Mutex、WaitGroup、Channel 等同步原语上的等待位置；Mutex Profile 更接近造成竞争的锁持有路径，其栈通常对应临界区结束、释放锁的位置。因此编辑器最好同时呈现“等待方”和“疑似持有方”。

Mutex 和 Block 采样默认并未开启，GoTune 本地启动目标时可以通过 Overlay 配置采样；连接远程服务时则需要服务端已经开启，或者给出明确提示。

## Channel 卡死示例

```go
func (q *Queue) Submit(job Job) {
    q.jobs <- job
}
```

源码旁显示：

```text
GoTune · Suspicious Blocking
19 goroutines blocked here
Stack unchanged for 12.4 seconds
No active receiver stack observed in 3 captures
Possible channel send deadlock

[查看全部 Goroutine] [查找 Channel 接收方] [Capture Trace]
```

注意用词应该是：

```text
Possible / Suspicious
```

不能直接宣布“这里一定死锁”。

## Mutex 竞争示例

```go
func (s *SessionTable) Get(id string) *Session {
    s.mu.Lock()
    defer s.mu.Unlock()
    return s.sessions[id]
}
```

源码旁显示：

```text
GoTune · Mutex Contention
47 goroutines waiting
6.4 s cumulative contention during the 30 s scenario
Likely hot critical section:
refresh.go:96

[查看等待方] [查看持锁调用路径] [与基线比较]
```

打开 `refresh.go:96`：

```text
This critical section is associated with 72% of sampled mutex contention.
```

这样你能直接看到：

- 谁在等；
- 哪段临界区可能持锁太久；
- 这是偶发等待还是持续不动；
- 修改后竞争时间是否下降。

## 它还应该区分三种东西

### 真死锁或逻辑卡死

```text
同一批 Goroutine 连续多轮停在同一同步点
业务操作完全没有推进
```

### 锁竞争

```text
程序仍然推进，但大量时间浪费在等待同一个锁
```

### 正常 I/O 等待

```text
大量 Goroutine 停在 netpoll / Read
但连接仍有流量，数量稳定
```

正常 I/O wait 不应该满屏标红。

# 场景三：定位某段代码为什么耗时

入口应该是：

```text
Investigate → Operation is slow
```

然后插件问的不是“抓 CPU Profile 吗”，而是：

```text
准备好复现该操作了吗？
[开始采集]
```

用户开始请求、上传、解题、转发流量或者跑压测，结束后点停止。

## GoTune 先判断是 CPU 慢还是等待慢

CPU Profile 只反映程序真正消耗 CPU 的部分。一个请求耗时 2 秒，如果其中 1.8 秒在等待网络或锁，CPU Profile 很可能只显示剩下的 200 毫秒。因此“代码耗时”工作流不能只抓 CPU，还要根据运行状况补充 Block、Goroutine 或 Trace。

结果可能是：

```text
Operation duration: 2.1 s

CPU work:       340 ms
Mutex wait:     510 ms
Network wait:   1.08 s
Other:          170 ms
```

这里的精确操作耗时拆分需要 Trace、应用区域标记或场景级计时支持；纯 CPU pprof 不能单独给出完整墙钟时间。

## 源码热度效果

例如：

```go
func encryptPacket(dst, src []byte) error {
    nonce := make([]byte, 12)
    copy(nonce, src[:12])
    return cipher.Seal(dst, nonce, src, nil)
}
```

编辑器可以显示：

```text
func encryptPacket(...)
────────────────────────────────────────────
GoTune · CPU Hotspot
Self CPU:        22.1%
Cumulative CPU:  34.8%
Main caller:     tunnel.writeLoop
Baseline delta:  +7.4%

[查看调用方] [查看被调用方] [分析分配] [比较基线]
```

每一行的左侧显示轻量热度条：

```text
85 │      nonce := make([]byte, 12)        Alloc 182 MiB / 30s
86 │ ██   copy(nonce, src[:12])            CPU 4.1%
87 │ ████ return cipher.Seal(...)          CPU self 18.0%
```

这样能区分：

- 函数 cumulative 很高，是因为它下面调用了昂贵函数；
- 函数 self 很高，耗时确实发生在自己内部；
- CPU 不高，但 Block 很高，真正问题是等待；
- CPU 能接受，但分配和 GC 把吞吐拖下来了。

火焰图还可以保留，但应该放在“查看完整证据”里，而不是要求所有用户先学会读图。

# 场景四：VPN 服务端流压测

这个非常适合做成 GoTune 的旗舰演示。

假设你有一个 VPN 服务端：

```text
客户端连接
→ 读取数据包
→ 解密
→ 路由查找
→ 转发
→ 加密
→ 写回连接
```

你跑 500 路并发流，发现吞吐一直卡在 700 Mbps，CPU 接近 100%，但不知道是：

- 加解密慢；
- 包复制太多；
- Buffer 分配太多；
- Session Map 锁竞争；
- 网络写阻塞；
- 单个 Goroutine 成了串行瓶颈；
- GC 抢走大量时间。

## 理想操作

第一次配置：

```text
Target：
VPN Server launch configuration

Load：
vpn-load-500 VS Code Task

Duration：
30 秒

Metrics：
loadgen 输出 JSON：
{
  "throughput_mbps": 712,
  "p95_ms": 41,
  "errors": 0
}
```

以后只点：

```text
Run VPN 500-stream Investigation
```

GoTune 自动：

```text
启动服务
→ 预热
→ 启动压测
→ Capture CPU
→ Capture alloc delta
→ Capture Block / Mutex
→ 前后 Heap 和 Goroutine 快照
→ 收集压测指标
→ 映射到源码
```

## 分析结果不应该先给一张大图

首页直接给：

```text
Why throughput plateaued near 712 Mbps

1. encryptPacket
   31.2% self CPU

2. newPacketBuffer
   812 MiB allocated in 30 s
   27.4% of business-code allocations

3. SessionTable.mu
   6.4 s sampled mutex contention
   41 goroutines waiting at peak

4. conn.Write
   11.2 s cumulative blocking
   likely socket backpressure

[Open all findings in source]
```

## 源码里看到的效果

```go
func (s *Session) writePacket(packet []byte) error {
    buf := make([]byte, maxPacketSize)
    s.table.mu.Lock()
    encryptPacket(buf, packet)
    _, err := s.conn.Write(buf)
    s.table.mu.Unlock()
    return err
}
```

理想的源码标注：

```text
buf := make([]byte, maxPacketSize)
────────────────────────────────────────────
Alloc 812 MiB / 30s · 27.4% of business allocations
Possible repeated packet buffer allocation
[分析逃逸] [查看调用路径] [Track after fix]

s.table.mu.Lock()
────────────────────────────────────────────
Mutex contention 6.4s · peak 41 waiters
Likely contended holder at session_table.go:204
[查看持锁路径]

encryptPacket(buf, packet)
────────────────────────────────────────────
CPU self 31.2% · primary throughput bottleneck
[查看调用方] [打开 CPU 证据]

s.conn.Write(buf)
────────────────────────────────────────────
Blocked 11.2s during scenario
Possible downstream/socket backpressure
[查看 Goroutine 栈] [Capture Trace]
```

这基本就是你说的：

> 跑一次流压测，瓶颈位置直接显示在代码旁边。

## 修改后直接复测

例如你做了：

- Buffer Pool；
- 减少一次包复制；
- Session Map 改成分片锁；
- 缩短持锁范围；
- 多个 Write 合并；
- 替换或优化加密调用。

再运行同一个场景：

```text
VPN 500-stream comparison

Metric                 Before       After        Delta
Throughput              712 Mbps     892 Mbps     +25.3%
p95 latency             41 ms        30 ms        -26.8%
CPU                     94%          86%          -8.5%
Allocations             812 MiB      231 MiB      -71.6%
Mutex contention        6.4 s        1.7 s        -73.4%
Goroutines              684          672          stable
```

其中吞吐和 p95 不是 pprof 自己能生成的，必须来自你的压测工具、Prometheus 指标或自定义 Metrics Adapter。GoTune 应该允许接入：

```text
JSON Lines
正则解析命令输出
Prometheus 查询
Go Benchmark 输出
自定义脚本
```

然后把业务指标和运行时 Profile 放在同一次场景里比较。

这会比单纯比较两个 CPU Profile 强很多，因为最终目标通常不是“某函数少了几个 CPU sample”，而是：

```text
同样 500 路流量下，吞吐有没有提高？
延迟有没有下降？
CPU 和内存成本有没有降低？
```

# 用户最终的真实使用方式

理想状态下，你日常只需要五步。

## 第一步：启动或连接

```text
Run with GoTune
Connect to pprof URL
Import production profile
```

当前 GoTune 已经具备 Overlay 注入、本地随机 pprof 端口、Profile 获取和源码跳转等基础能力，因此底层不用推倒重来。

## 第二步：选择症状

```text
CPU high / throughput low
Memory keeps growing
Too many allocations / GC
Request stuck / possible deadlock
Latency is high
```

## 第三步：运行场景

```text
手动复现
运行 VS Code Task
运行 Benchmark
运行自定义压测命令
```

## 第四步：直接在代码里解决

源码旁显示：

- CPU self / cumulative；
- Live Heap 增长；
- Allocation delta；
- Goroutine 增长；
- Channel / WaitGroup 阻塞；
- Mutex 竞争；
- 与 Baseline 的变化；
- 下一步动作。

## 第五步：Verify Fix

```text
Run same scenario again
```

插件自动保证：

- 同一个目标；
- 同一个压测命令；
- 同一个预热时间；
- 同一个采集时长；
- 同一类指标；
- 保留 Git Commit 和修改信息。

然后给出真正有意义的 Before / After。

# 它和原始 pprof 的本质差异

| 原始 pprof | GoTune 愿景 |
|---|---|
| 用户选择 Profile 类型 | 用户选择问题症状 |
| 显示函数、调用图、火焰图 | 直接显示源码位置和问题证据 |
| 一次孤立采集 | 一个完整的复现或压测场景 |
| 需要自己判断下一步 | 每个 Finding 带下一步动作 |
| 手动找源码 | 点击或自动打开对应源码 |
| 手工比较两次结果 | 同场景自动 Baseline/Current 对比 |
| 主要看 CPU/内存内部指标 | 同时关联吞吐、延迟、错误率等业务指标 |
| 图是主界面 | 源码是主界面，图是高级证据 |

所以重点不在于把 pprof 的图做漂亮一点。

**甚至可以不急着重新设计一套巨复杂的 Flame Graph。**

先把这几个东西做透：

```text
症状入口
场景执行
自动采证
源码标注
问题解释
下一步动作
同场景验证
```

原始 pprof Web UI、Graph、Flame Graph 可以保留为：

```text
Advanced Evidence
```

高手需要时仍然能打开。

# 最终产品效果

做到位后，GoTune 给人的感觉应该是：

> 我不需要是一名 pprof 专家。
>
> 我只需要告诉插件“内存一直涨”“请求卡住”或者“VPN 压测吞吐上不去”，跑一次真实场景，它就会把证据贴到对应代码旁边，告诉我优先处理哪里，并在修改后用相同场景验证效果。

最适合写在项目首页的一句话可以是：

> **GoTune turns Go runtime profiles into actionable source-code findings and verifies performance fixes under repeatable workloads.**

中文就是：

> **GoTune 把 Go 运行时 Profile 转化为源码旁可执行的性能结论，并通过可重复的真实负载验证优化效果。**

当前项目已经有不少底层拼图，接下来最重要的不是继续增加 Profile 类型，而是把它们重新组织成三个主工作流：

```text
排查慢和吞吐瓶颈
排查内存与 Goroutine 增长
排查卡住、死锁与锁竞争
```

再用一个统一的：

```text
Run Scenario → Fix in Source → Verify
```

把它们串起来。这样 GoTune 才会从“功能很多但不知道怎么用”，变成一个真正比 pprof 网页版方便很多的性能开发工具。
