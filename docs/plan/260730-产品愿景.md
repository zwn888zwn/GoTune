# 当前收敛目标：简单、源码优先

GoTune 当前阶段不再追求增加更多性能工具，而是集中完成一个目标：

> **让用户不需要学习 pprof，就能从当前代码或全局瓶颈出发，定位值得优化的源码，并用相同条件验证修改是否有效。**

插件只保留三条一级使用路径：

```text
分析当前函数
→ 自动采集 CPU、分配和 GC 后存活内存
→ 只展示与当前函数、调用方和下游函数有关的证据
→ 修改后验证

全局寻找瓶颈
→ 按 CPU、存活内存、分配、等待或延迟查看
→ 使用成熟的 Graphviz 调用图和瓶颈排行
→ 点击节点直接回到源码

排查已知问题
→ 描述 CPU 高、内存增长、Goroutine 堆积、锁竞争或操作慢
→ GoTune 自动选择并组合证据
→ Findings 落到源码和下一步动作
```

## 主界面做减法

默认左侧只展示：

```text
Analyze
├── Analyze current function
├── Find global bottlenecks
├── Investigate a known problem
└── Current target / Stop

Findings
└── 可以直接打开源码的结论
```

下列能力继续保留，但统一放入 **Advanced Evidence**，不与主流程竞争：

- 手动 Capture CPU、Heap、Allocations、Mutex、Block 和 Goroutine；
- 原始 Profile Sessions、Top、Flame Graph、Call Tree 和 Source；
- Trace 原始时间线；
- Performance Scenario 管理；
- Contention、远程 pprof、导入 Profile 和手动目标控制。

## 不重新发明比 pprof 更差的图

pprof 和 Graphviz 已经擅长全局调用拓扑、热点大小和路径宽度。GoTune 不再用表格式“树”替代它，而是在成熟调用图之上增加 IDE 能力：

- 图节点显示 self 和 with-callees 占比；
- 点击节点打开准确的本地源码和 Go Symbol；
- 从源码函数定位到活动调用图；
- 聚焦当前函数的调用方和昂贵下游；
- 自动映射容器或远程 Profile 的源码路径；
- 修改后在相同路径上展示改善或退化。

Graphviz 不可用时，Top、源码行证据和 Flame Graph 仍可作为降级结果。

## 每项功能的准入标准

以后新增或保留一项功能前，必须回答：

> 它是否利用编辑器中的源码、符号、引用、运行入口或修改记录，替用户减少了一次 pprof 判断？

如果答案是否定的，它只能属于高级证据，不能进入主流程。

当前版本的验收标准：

- 不理解 `flat`、`cum`、`inuse_space` 的用户也能开始；
- 从当前函数到开始采集不超过两次点击；
- 每个重要结果都能跳到业务源码；
- 全局调用图与源码能够双向定位；
- 结果明确区分 CPU、分配、存活内存、等待和墙钟耗时；
- 修改后能够复用相同证据协议验证；
- 原始 pprof 随时可打开，但默认不干扰主流程。

---

对，真正的愿景不是：

> **在 VS Code 里做一个更漂亮的 pprof Viewer。**

而应该是：

> **像调试功能 Bug 一样，调试 Go 的性能问题。**

最终体验应该是：

```text
从编辑器中的函数或代码行直接开始
→ 查看它在当前证据中的 CPU、内存、分配、调用和等待情况
→ 打开完整调用路径或采集缺少的证据
→ 修改代码并验证

或者：

启动或连接 Go 服务
→ 选择“我遇到了什么问题”
→ 跑一次真实操作或压测
→ GoTune 自动采集合适的证据
→ 瓶颈直接显示在源码旁边
→ 告诉你为什么可疑、下一步看哪里
→ 修改代码
→ 用完全相同的场景重新跑
→ 告诉你到底有没有改善
```

这其实就是最初设计文档的核心：`哪里慢 → 为什么慢 → 怎么改 → 是否真的变快`，而不是把 CPU、Heap、Mutex、Trace 做成一排按钮。

# 一句话定位

**GoTune 是源码中心的 Go 性能 Debugger。**

它既能从问题出发自动组合 pprof 等运行时证据，也能从代码出发，随时查看当前函数或代码行的 CPU、分配、存活内存、调用和等待情况，并通过可重复负载验证优化效果。

pprof 仍然是底层证据来源，但用户不需要先理解：

- 现在该抓 `inuse_space` 还是 `alloc_space`；
- 该看 CPU 还是 Block；
- Mutex 图里为什么标的是 `Unlock`；
- 一个函数 cumulative 很高到底是不是它本身慢；
- 两份 Profile 到底能不能直接对比。

官方 pprof 提供 CPU、Heap、Goroutine、Block、Mutex 等运行时证据；其中 CPU 只表示真正占用 CPU 的时间，不包含睡眠和 I/O 等待，Block 表示同步原语上的等待，Mutex 表示锁竞争。GoTune 的价值是自动选择、组合、解释这些证据，并把它们落回源码。

可以简单理解成：

```text
pprof：给你检查报告和影像
GoTune：带你定位病灶、打开对应代码、修改后复查
```

GoTune 应该提供两条同等重要的一级入口：

```text
从源码出发
→ 我正在看的函数或代码有什么性能证据？

从问题出发
→ 我遇到的是 CPU 高、内存增长、分配过多还是请求卡住？
```

前者让熟悉代码的开发者立即检查当前函数，不需要先创建场景或切换到分析面板；后者让不熟悉 pprof 的用户只描述症状，由 GoTune 选择和组合工具。两条路径最终汇合到同一个源码工作区和验证流程。

# Profile、性能调查与可重复场景

Profile 不应该是用户需要管理的最高层对象，但“性能场景”也不是所有操作的前置条件。更合适的三层关系是：

```text
Investigation：一次性能调查
├── Problem：要回答的问题
├── Target：被分析的程序
├── Captures：CPU、Heap、Goroutine 等原始证据
├── Findings：落到源码的结论
└── Verification：修改后的验证结果

Scenario：可重复运行的 Investigation 模板
├── Workload
├── Warmup
├── Capture protocol
└── Success metrics

Profile：Investigation 中的一种底层证据
```

临时检查当前函数、导入生产 Profile、连接已有服务时，可以直接创建轻量 Investigation，不应强迫用户先配置场景。需要可靠复测、持续优化或压测时，再把 Investigation 保存为可重复的 **Performance Scenario**。

现在插件主要围绕一个个 Profile Session 展开。对于需要重复验证的工作，应该围绕一个可重复的 Performance Scenario 展开：

```text
性能场景
├── Target：哪个程序、怎么启动
├── Workload：怎样复现问题
├── Warmup：预热多久
├── Capture：采集哪些证据、采集多久
├── Success Metrics：怎样才算变好
└── Baseline：修改前是什么表现
```

例如你的 VPN 服务端可以保存一个场景：

```text
场景：VPN 500 路流压测

目标：
  VS Code Launch Configuration: VPN Server Dev

预热：
  10 秒

压测：
  VS Code Task: vpn-load-500
  或 go run ./cmd/loadgen -streams 500 -duration 30s

自动采集：
  CPU 30 秒
  Allocation delta 30 秒
  Heap 压测前后快照
  Mutex / Block delta
  Goroutine 前后快照
  GC 和运行时趋势

成功指标：
  吞吐 Mbps
  p95 延迟
  CPU
  alloc/GB
  Heap 增长
  Mutex wait
  Goroutine 数量
```

以后不是每次重新想“该点哪个按钮”，而是：

```text
打开项目
→ Run “VPN 500 路流压测”
→ 等压测完成
→ 查看源码瓶颈
```

这才是一个开发者会长期使用的工具。

# 场景零：从编辑器检查当前函数或代码

这是 GoTune 与普通 pprof Viewer 最直接的差异，也应该是开发者使用频率最高的入口之一。

用户正在阅读代码时，可以在函数、方法或代码行上直接执行：

```text
GoTune: Inspect Current Function
GoTune: Show in Active Evidence
GoTune: Capture Evidence for This Code
GoTune: Compare Current Function with Baseline
```

如果已有活动 Profile，GoTune 应该立即把当前 Go Symbol 与 Profile 中的函数、内联栈和源码行关联起来。如果证据不足，再提示采集 CPU、Allocation、Heap、Block 或其他匹配证据，而不是先把用户带到一排 pprof 按钮。

## 函数旁应该看到什么

CPU 证据：

```text
GoTune · encryptPacket
Self CPU             18.2%
With callees         34.7%
Primary caller       tunnel.writeLoop
Baseline delta       +7.4%

[查看调用方] [查看被调用方] [打开完整 CPU 证据] [修改后验证]
```

内存和分配证据：

```text
GoTune · newPacketBuffer
Allocated            812 MiB / 30s
Allocation objects   1.42 M / 30s
Still live after GC  38.4 MiB
Three-round growth   +12.6 MiB

[查看分配路径] [分析逃逸] [检查内存增长] [修改后验证]
```

等待证据：

```text
GoTune · SessionTable.Get
Mutex wait           320 ms
Blocked goroutines   24
Stable captures      3

[查看等待栈] [查看相关调用路径] [Capture Trace] [修改后验证]
```

## 编辑器与 pprof 必须双向联动

```text
Profile / Flame Graph / Call Tree
→ 点击函数
→ 打开准确源码和 Go Symbol
→ 显示该函数的组合证据

源码函数 / 代码行
→ Show in Active Evidence
→ 定位 Profile、调用路径和对应样本
→ 根据证据类型给出下一步动作
```

编辑器侧需要充分利用：

- CodeLens：在函数声明处显示最重要的性能摘要和动作；
- Hover：解释 self、cumulative、分配、存活和 baseline delta；
- 行热度：区分自身消耗与包含下游调用的累计消耗；
- Gutter：轻量标记 CPU、内存增长、分配和阻塞证据；
- Diagnostics：展示逃逸、持续增长和可疑阻塞，但避免把普通性能建议标成错误；
- Code Action：提供查看调用链、采集缺少证据、设为优化目标和重新验证；
- 编辑器右键：从当前真实 Go Symbol 发起分析，而不是选择附近热点；
- 可见编辑器同步：切换活动证据后立即更新所有已打开的相关 Go 文件。

同一个函数可能同时关联多种证据。GoTune 不应该让后打开的 Profile 覆盖之前的结果，而应该在统一的 Function Evidence 中组合展示 CPU、Allocation、Live Heap、Goroutine、Mutex、Block 和 Baseline。

## “函数占用内存”必须准确表达

pprof 可以把分配量和存活内存归因到分配调用栈，但不能天然提供完整对象引用图。因此 GoTune 应该区分：

- `alloc_space`：该函数及调用路径累计分配的字节；
- `alloc_objects`：累计创建的对象数；
- `inuse_space`：由该分配路径创建、采集时仍存活的字节；
- `inuse_objects`：采集时仍存活的对象数；
- 多轮 GC 后，该位置对应的存活内存是否持续增长。

界面应写“由此分配路径产生的存活内存”或“疑似泄漏分配位置”，不能简单写成“这个函数当前持有多少内存”，也不能仅凭 Heap Profile 宣布精确持有者。

# 场景一：排查内存泄漏

## 用户怎么操作

你只需要选择：

```text
Investigate → Memory keeps growing
```

然后：

```text
启动服务
→ 执行一段真实业务操作
→ 或者运行压测任务
→ 点击结束分析
```

不应该要求用户先决定抓 Heap 还是 Alloc。

## GoTune 在背后做什么

它自动组合：

1. 压测前 Heap 基线；
2. 压测过程中的 Allocation delta；
3. 多轮 Heap 快照；
4. 本地测试环境可在快照前执行 GC；
5. Goroutine 数量和重复栈趋势；
6. GC 次数、Heap、Allocation rate 趋势。

`net/http/pprof` 本身支持在 Heap 快照前触发 GC，也支持按指定时间生成 alloc、heap、block、mutex 等 delta profile。当前 GoTune README 已经有三轮 GC 后的内存增长检查和 Goroutine 多轮检查，这些能力可以直接被组织进该工作流。

然后插件先帮助你判断是哪一类问题：

### A. 真正的存活内存持续上涨

```text
Heap after GC：

第 1 轮：126 MiB
第 2 轮：168 MiB
第 3 轮：211 MiB

结论：
压测停止并执行 GC 后，存活内存仍连续增长。
疑似存在对象长期被引用。
```

### B. 不是泄漏，只是分配太猛

```text
alloc_space：2.8 GiB / 30s
inuse_space：稳定在 130 MiB

结论：
存活内存稳定，没有明显泄漏。
主要问题是临时对象过多，导致 GC 压力。
```

### C. Goroutine 泄漏带着对象一起泄漏

```text
Goroutine：
320 → 670 → 1,020

其中 700 个 Goroutine 停在：
session.go:132
<-ctx.Done()

对应调用路径：
acceptLoop
→ newSession
→ startReadLoop
```

这时问题可能不是某个 `[]byte` 单独泄漏，而是 Session Goroutine 没退出，闭包、连接、Buffer 都被一起保留。

## 源码旁边应该看到什么

例如打开 `session.go`：

```go
func (m *Manager) AddSession(id string, conn net.Conn) {
    s := newSession(conn)
    m.sessions[id] = s
    go s.readLoop()
}
```

理想中的编辑器效果：

```text
m.sessions[id] = s
────────────────────────────────────────────
GoTune · Live Heap
+38.4 MiB across 3 post-GC captures
+18,624 live objects
Allocation path:
acceptLoop → AddSession → newSession
[查看调用链] [查看相关 Goroutine] [标记为修复目标]
```

在 `go s.readLoop()` 上方：

```text
GoTune · Goroutine Growth
+512 goroutines · same stack in 3 captures
Related live heap growth: +31.6 MiB
[查看完整栈] [查找退出路径]
```

你不需要在火焰图里找函数名，再手动切回 VS Code 搜代码。

## 修改后怎么验证

例如你补上：

```go
defer delete(m.sessions, id)
defer conn.Close()
```

重新运行同一个场景后：

```text
                         Before       After       Delta
Live heap growth         +84 MiB      +3.1 MiB    -96.3%
Goroutine growth         +512         +2          -99.6%
Allocation rate          92 MiB/s     74 MiB/s    -19.6%
```

然后源码旁边的提示从“持续增长”变成：

```text
Verified · no persistent growth in the last 3 captures
```

## 这里不能过度承诺

标准 Go Heap Profile 能告诉你：

- 哪些调用栈分配了存活对象；
- 哪些函数贡献了大量存活内存；
- 多轮采集后哪些对象持续增长。

但它不像某些 JVM Heap Dump 工具那样天然提供完整的“对象 A 被 Map B 的字段 C 引用”对象图。因此 GoTune 应该显示：

> 疑似泄漏分配位置和相关运行时证据

而不是假装仅凭 pprof 就百分之百知道精确持有者。

# 场景二：排查死锁、卡住和锁竞争

用户看到的入口应该是：

```text
Investigate → Request stuck or possible deadlock
```

而不是先让用户选 Goroutine、Block、Mutex 或 Trace。

## GoTune 自动组合的证据

它可以依次做：

```text
第 1 次 Goroutine 快照
等待数秒
第 2 次 Goroutine 快照
第 3 次 Goroutine 快照
Block delta
Mutex delta
必要时再 Capture Trace
```

Block Profile 记录 Goroutine 在 Mutex、WaitGroup、Channel 等同步原语上的等待位置；Mutex Profile 更接近造成竞争的锁持有路径，其栈通常对应临界区结束、释放锁的位置。因此编辑器最好同时呈现“等待方”和“疑似持有方”。

Mutex 和 Block 采样默认并未开启，GoTune 本地启动目标时可以通过 Overlay 配置采样；连接远程服务时则需要服务端已经开启，或者给出明确提示。

## Channel 卡死示例

```go
func (q *Queue) Submit(job Job) {
    q.jobs <- job
}
```

源码旁显示：

```text
GoTune · Suspicious Blocking
19 goroutines blocked here
Stack unchanged for 12.4 seconds
No active receiver stack observed in 3 captures
Possible channel send deadlock

[查看全部 Goroutine] [查找 Channel 接收方] [Capture Trace]
```

注意用词应该是：

```text
Possible / Suspicious
```

不能直接宣布“这里一定死锁”。

## Mutex 竞争示例

```go
func (s *SessionTable) Get(id string) *Session {
    s.mu.Lock()
    defer s.mu.Unlock()
    return s.sessions[id]
}
```

源码旁显示：

```text
GoTune · Mutex Contention
47 goroutines waiting
6.4 s cumulative contention during the 30 s scenario
Likely hot critical section:
refresh.go:96

[查看等待方] [查看持锁调用路径] [与基线比较]
```

打开 `refresh.go:96`：

```text
This critical section is associated with 72% of sampled mutex contention.
```

这样你能直接看到：

- 谁在等；
- 哪段临界区可能持锁太久；
- 这是偶发等待还是持续不动；
- 修改后竞争时间是否下降。

## 它还应该区分三种东西

### 真死锁或逻辑卡死

```text
同一批 Goroutine 连续多轮停在同一同步点
业务操作完全没有推进
```

### 锁竞争

```text
程序仍然推进，但大量时间浪费在等待同一个锁
```

### 正常 I/O 等待

```text
大量 Goroutine 停在 netpoll / Read
但连接仍有流量，数量稳定
```

正常 I/O wait 不应该满屏标红。

# 场景三：定位某段代码为什么耗时

入口应该是：

```text
Investigate → Operation is slow
```

然后插件问的不是“抓 CPU Profile 吗”，而是：

```text
准备好复现该操作了吗？
[开始采集]
```

用户开始请求、上传、解题、转发流量或者跑压测，结束后点停止。

## GoTune 先判断是 CPU 慢还是等待慢

CPU Profile 只反映程序真正消耗 CPU 的部分。一个请求耗时 2 秒，如果其中 1.8 秒在等待网络或锁，CPU Profile 很可能只显示剩下的 200 毫秒。因此“代码耗时”工作流不能只抓 CPU，还要根据运行状况补充 Block、Goroutine 或 Trace。

结果可能是：

```text
Operation duration: 2.1 s

CPU work:       340 ms
Mutex wait:     510 ms
Network wait:   1.08 s
Other:          170 ms
```

这里的精确操作耗时拆分需要 Trace、应用区域标记或场景级计时支持；纯 CPU pprof 不能单独给出完整墙钟时间。

## 源码热度效果

例如：

```go
func encryptPacket(dst, src []byte) error {
    nonce := make([]byte, 12)
    copy(nonce, src[:12])
    return cipher.Seal(dst, nonce, src, nil)
}
```

编辑器可以显示：

```text
func encryptPacket(...)
────────────────────────────────────────────
GoTune · CPU Hotspot
Self CPU:        22.1%
Cumulative CPU:  34.8%
Main caller:     tunnel.writeLoop
Baseline delta:  +7.4%

[查看调用方] [查看被调用方] [分析分配] [比较基线]
```

每一行的左侧显示轻量热度条：

```text
85 │      nonce := make([]byte, 12)        Alloc 182 MiB / 30s
86 │ ██   copy(nonce, src[:12])            CPU 4.1%
87 │ ████ return cipher.Seal(...)          CPU self 18.0%
```

这样能区分：

- 函数 cumulative 很高，是因为它下面调用了昂贵函数；
- 函数 self 很高，耗时确实发生在自己内部；
- CPU 不高，但 Block 很高，真正问题是等待；
- CPU 能接受，但分配和 GC 把吞吐拖下来了。

火焰图还可以保留，但应该放在“查看完整证据”里，而不是要求所有用户先学会读图。

# 场景四：VPN 服务端流压测

这个非常适合做成 GoTune 的旗舰演示。

假设你有一个 VPN 服务端：

```text
客户端连接
→ 读取数据包
→ 解密
→ 路由查找
→ 转发
→ 加密
→ 写回连接
```

你跑 500 路并发流，发现吞吐一直卡在 700 Mbps，CPU 接近 100%，但不知道是：

- 加解密慢；
- 包复制太多；
- Buffer 分配太多；
- Session Map 锁竞争；
- 网络写阻塞；
- 单个 Goroutine 成了串行瓶颈；
- GC 抢走大量时间。

## 理想操作

  "throughput_mbps": 712,

→ 启动压测

# 它和原始 pprof 的本质差异

| 原始 pprof | GoTune 愿景 |
|---|---|
| 用户选择 Profile 类型 | 用户检查当前代码或选择问题症状 |
| 显示函数、调用图、火焰图 | 直接显示源码位置和问题证据 |
| 一次孤立采集 | 一次关联源码与多种证据的 Investigation，必要时保存为场景 |
| 需要自己判断下一步 | 每个 Finding 带下一步动作 |
| 手动找源码 | 点击或自动打开对应源码 |
| Profile 与编辑器相互独立 | Profile 和当前 Go Symbol 双向定位 |
| 一次只看一种 Profile | 在函数旁组合 CPU、内存、分配和等待证据 |
| 手工比较两次结果 | 同场景自动 Baseline/Current 对比 |
| 主要看 CPU/内存内部指标 | 同时关联吞吐、延迟、错误率等业务指标 |
| 图是主界面 | 源码是主界面，图是高级证据 |

所以重点不在于把 pprof 的图做漂亮一点。

**甚至可以不急着重新设计一套巨复杂的 Flame Graph。**

先把这几个东西做透：

```text
当前函数检查
Profile 与源码双向定位
症状入口
场景执行
自动采证
源码标注
问题解释
下一步动作
同场景验证
```

原始 pprof Web UI、Graph、Flame Graph 可以保留为：

```text
Advanced Evidence
```

高手需要时仍然能打开。

# 产品优先级

后续开发不应按“还能支持哪一种 pprof”排序，而应按源码交互闭环排序：

```text
1. Inspect Current Function
   当前 Go Symbol ↔ Profile 函数、调用路径、源码行

2. Function Evidence
   在函数旁组合 CPU、Allocation、Live Heap、等待和 Baseline

3. Guided Investigation
   根据症状自动选择和解释已有采集能力

4. Repeatable Scenario and Verify
   固定目标、负载、预热、采集协议和成功指标

5. Advanced Evidence
   Flame Graph、完整 Call Tree、Trace 和原始 Profile
```

判断一个功能是否值得优先开发，可以问：

```text
它是否让用户更容易从当前代码发现性能证据？
它是否让 Profile 与编辑器之间的往返更少？
它是否给出了与证据类型匹配的下一步动作？
它是否能在修改后可靠回答“有没有变好”？
```

如果答案都是否定的，即使它增加了一种新图表或新 Profile，也不应进入主流程。

# 最终产品效果

做到位后，GoTune 给人的感觉应该是：

> 我不需要是一名 pprof 专家。
>
> 我可以直接检查当前函数，也可以告诉插件“内存一直涨”“请求卡住”或者“VPN 压测吞吐上不去”。GoTune 会把 pprof 等证据贴到对应代码旁边，告诉我优先处理哪里，并在修改后用相同场景验证效果。

最适合写在项目首页的一句话可以是：

> **GoTune connects Go runtime evidence with the code you are editing, turns profiles into actionable findings, and verifies fixes under repeatable workloads.**

中文就是：

> **GoTune 把 Go 运行时证据与正在编辑的代码连接起来，将 Profile 转化为源码旁可执行的性能结论，并通过可重复的真实负载验证优化效果。**

当前项目已经有不少底层拼图，接下来最重要的不是继续增加 Profile 类型，而是把它们重新组织成四个主工作流：

```text
随时检查当前函数或代码的性能证据
排查慢和吞吐瓶颈
排查内存与 Goroutine 增长
排查卡住、死锁与锁竞争
```

再用一个统一的：

```text
Inspect Code / Run Scenario → Fix in Source → Verify
```

把它们串起来。这样 GoTune 才会从“功能很多但不知道怎么用”，变成一个真正比 pprof 网页版方便很多的性能开发工具。
